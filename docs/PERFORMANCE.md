# 性能：探测、优化与待议项

每次渲染都走的路径（样式定义的查找、属性合并、样式登记、参数比较、依赖收集）与浏览器端的初始化、DOM 变化处理。
基准在 `tests/Rune.Benchmarks`（BenchmarkDotNet，见它的 README）；浏览器端的数字是在文档站（Release、本机、HTTP/1.1、未压缩）里用 Performance API 与给
`querySelectorAll` / `matches` 计数量的。

计时类基准要在机器空闲时跑：2026-11-06 那一轮跑的时候机器平均负载 80% 以上（WSL、IDE 在后台），渲染基准的耗时前后差到 60%，
所以渲染只看**分配量**（确定的），耗时看微基准（倍数差远大于噪声）。

## 1. 2026-11-06 这一轮

### C#：每次渲染的路径

| 路径 | 之前 | 之后 | 改法 |
| ---- | ---- | ---- | ---- |
| `Css.Define`（静态） | 26 ns / 24 B | 20 ns / 0 B | `GetOrAdd` 用带状态的重载，不再每次分配闭包 |
| `Css.Define`（按键：档位、配方） | 52 ns / 56 B | 25 ns / 0 B | 按键与结果的类型分开放（`Keyed<TKey, T>`），键不装箱；热重载时一起清 |
| `Recipe.Of`（图标的配方） | 125 ns / 136 B | 79 ns / 0 B | 同上（配方的键是元组） |
| `Attrs.Merge`（只有样式） | 54 ns | 7 ns | 已编译的样式记住最近登记进的登记表，同一作用域里不再加锁查表 |
| `Attrs.Merge`（部件层：样式 + `data-scope` / `data-part`） | 296 ns / 304 B | 7 ns / 0 B | 合并结果记在最靠后的非空层上，同样的几层（引用相同，Attrs 创建后不变）直接复用 |
| `Attrs.Merge`（部件 + Rest + 受管） | 625 ns / 816 B | 13 ns / 0 B | 同上 |
| `Attrs.MergeProps` / `Layer` | 518 ns / 960 B | 4 ns / 0 B | 同上；结果是同一个对象，子组件按引用比较 `Sx` 参数时就会跳过渲染 |
| 依赖收集（不读信号的组件） | 每次渲染一个字典、一个 HashSet | 不分配 | 读到信号时才建字典，没有依赖时订阅集合为 null |
| 整页渲染（按钮、徽标、图标各 100 个） | 首次 1579 KB；父级重渲染、子组件不变 131 KB；按钮全部重渲染 360 KB | 1344 KB；71 KB；217 KB | 以上各项合计 |
| 参数比较（6 个参数） | 520 ns / 72 B | 不变 | 试过 `MethodInvoker` 代替 `PropertyInfo.GetValue`，没有差别，撤回；剩下的是枚举、布尔的装箱与按名字查属性（见待议项） |

`RuneStyles` 在新规则登记时排一次渲染：之前每条规则排一次（第一次渲染一页登记几百条），现在排着队时不再排。

另：bUnit 不适合测渲染性能。它每渲染一个组件就重新生成整页 HTML 再解析，组件一多就是平方级（100 组按钮改一个参数要 183 ms、105 MB），
盖过了要测的东西。基准用自己的最小渲染器（`BenchRenderer`：只有 Blazor 的渲染与比较，没有输出）。

### 浏览器：启动与 DOM 变化

| 项 | 之前 | 之后 | 改法 |
| -- | ---- | ---- | ---- |
| Blazor 启动前等的 JS | 初始化器连同它静态导入的约 40 个模块（本机从初始化器到最后一个模块约 0.7 s，WebAssembly 运行时在这之后才开始下载） | 只等 24 KB 的入口；主体（`js/core/runtime.js` 与模块）在入口执行时开始后台加载，与 WebAssembly 运行时的下载并行 | 入口同步注册自定义事件，并在 document 上为每种事件占位（保持排在 Blazor 的事件委托之前：先不占位时，负载高的 WebAssembly 端到端测试里 Combobox 的高亮被清掉），主体到了再挂处理函数 |
| 增强导航进入 Select 文档页（约 2800 个新元素）时找要处理的元素 | `querySelectorAll` 2833 次（30 ms）、`matches` 约 10.7 万次（89 ms） | 42 次（3 ms）、1437 次（2 ms） | Blazor 先插父元素再逐个插子元素，一棵新子树每个节点各有一条变化记录：只从这一批最外层的新节点往下找；根节点先用合并的选择器问一次；列表、标签行按元素去重，每批处理一次 |
| 跟随指针的装饰（`data-rune-pointer`） | 鼠标一动，每帧在整个文档里找一遍（页面上没有这种元素也找） | 插入时登记，每帧只走登记的；一个都没有时不排帧 | |

## 2. 分段输出与级联层之后（2026-11-06，vue-tsx-pro 阶段 1）

- 合并路径的耗时、分配不变（结果按层缓存，分段只在第一次合并时多编译几段）；整页渲染的分配：首次 1344 → 1351 KB，按钮全部重渲染 217 → 220 KB。
- 样式文本（测试台的静态页，含主题变量）：Button 508 → 515 KB、Select 296 → 297 KB、Table 272 → 271 KB、Form 336 → 334 KB、Card 289 → 291 KB。
  演示页上定制、`Sx` 的组合不多，分段省下的少，每条规则外面多包的 `@layer rune.s{k}{…}` 又多了一点；组合多的应用（同一组件多种档位 × 定制 × 使用方样式）才省得明显。
- 计算样式：`tools/style-snapshot` 前后比对全部文档页（亮暗两套、强制 :hover / :focus-visible / :active），真实差异为 0
  （差异只有改了文字的样式指南页、动画中途的取值，以及改造前那份在两个元素上亮暗不一致的不稳定值）。

## 3. 文档站的 WebAssembly 首次加载（2026-11-09）

线上文档站（静态导出，整站是 WebAssembly 的交互根）打开 Button 页：HTML 0.7 秒显示，.NET 的文件 1.7 秒下载完，点击到 4.5 秒才生效
（之前点的被丢掉）。慢在 WebAssembly 下载与启动，按体积从大到小处理：

| 项 | 之前 | 之后 | 改法 |
| -- | ---- | ---- | ---- |
| 启动时下载的 .NET 文件（Button 页，解压后） | 71 个，19.8 MB | 64 个，14.9 MB | 下面几项合计 |
| Rune.Docs.Content | 4.86 MB | 2.42 MB | 示例源码（2.6 MB）与组件库的 XML 文档注释（1.4 MB）不再嵌进程序集：服务端 Rune.Docs.Server 生成，浏览器按类型下载 `/_docs/…` |
| System.Private.Xml | 537 KB | 不再下载 | API 表的说明在服务端读 XML |
| Rune.Icons | 1.05 MB | 91 KB | 图标库的列表改为服务端生成的 JSON（只有图标页下载），浏览器不再反射 Lucide 全集，裁剪去掉没用到的图标 |
| Rune.Charts、Rune.Charts.Maps、Rune.UI.Area | 启动时下载 | 进入用到的页面前才下载 | `BlazorWebAssemblyLazyLoad` + Routes 的 OnNavigateAsync（`LazyAssemblies`，`LazyAssemblyTests` 检查别的页面没用到） |
| ICU 数据 | 1.49 MB，Cloudflare 不压缩 | 同样大小，传输时压缩 | 导出写 `_headers` 把 `.dat` 标成 application/wasm；分片（CJK）不行：Calendar、DateField 有德文、Provider 有阿拉伯文的示例 |
| 每页的 HTML（Button 页） | 950 KB（gzip 81 KB） | 837 KB（gzip 72 KB） | 十六套主题的变量（120 KB）放进按内容哈希命名的外部样式表（`ThemeStylesheet`），只下载一次 |
| 显示代码 | 等 WebAssembly 启动完才能点 | 页面一出来就能点 | Collapse 的触发器在 JS 里切换（`data-rune-disclose`） |

没采用的：文档数据随页面带给浏览器（PersistentComponentState）。框架的 JSON 把中文转义成 \uXXXX、再套两层 base64，Button 页要多 143 KB（gzip 31 KB），
而接管后源码区是收着的、API 表在页底，直接下载几 KB 的文件看不出空白。

### 再量一遍（2026-11-13，线上 Button 页，无头 Chromium）

加载过程：HTML（预渲染，857 KB，压缩后 66 KB）约 1.1 秒显示 → blazor.web.js → dotnet.js → 58 个 .wasm 与 ICU 数据（压缩后 5.3 MB）约 4 秒下完
→ .NET 启动、加载程序集（约 1.3 秒）→ 第一次交互渲染（一个约 3.5 秒的长任务，整页的节点换一遍）→ 取这一页的文档数据（22 个小文件）、渲染 API 表。
再次打开时 .wasm 全部来自缓存，但 .NET 启动与第一次渲染的 5 秒左右不变：这是解释执行的固定开销（AOT 能缩短，下载会大两三倍，没做）。

| 项 | 之前 | 之后 | 改法 |
| -- | ---- | ---- | ---- |
| Rune 的 JS 装好（`data-rune-ready`） | 首次约 10 秒、再次约 7.4 秒 | 首次约 1.5 秒、再次约 1 秒，在 WebAssembly 开始编译之前 | 模块原来是一层层发现的（页面 → blazor.web.js → 初始化器 → runtime.js → 它导入的 40 个模块），最后一层开始下载时 .NET 已经占着主线程。文档站的页面头加 `ModulePreloads`：入口、runtime.js 与它静态导入的模块都写成 `modulepreload`（带 import map 里同样的 integrity，不带的话浏览器不认预加载、再下载一遍） |
| 带哈希的 `_content` 文件（Rune 的 JS、样式、图片，55 个请求） | `max-age=0`，再次打开逐个回源确认 | 长期缓存（immutable），再次打开只有 HTML（压缩后 67 KB）走网络 | 导出时只留带哈希的文件，原名写成 302 跳到带哈希的地址（`_redirects`），整个 `_content` 目录就能长期缓存；`_framework` 同样处理 |
| 文档数据（`_docs`，每页二十来个小文件） | `max-age=0` | 缓存十分钟 | `_headers` |
| 地图数据（Rune.Charts.Maps，压缩后 171 KB） | 任何图表页都下载 | 只有 MapChart 页下载 | `LazyAssemblies` 按页面分，`LazyAssemblyTests` 检查别的图表页没用到 |

部署后在线上复测（同一页）：.NET 接管（整页节点换成交互的）首次约 9.7 秒、再次约 5.4 秒，与之前相当（首次 10.4 秒、再次 7.1 秒；每次测有一两秒的出入），
这一段没有动。逐页打开全部 118 页，没有控制台错误（avatar、image 两页的 404 是示例故意的）。

复测用的脚本思路：CDP 的 Network 事件数请求与字节（冷、热各开一次），页面里记 `WebAssembly.compileStreaming` / `instantiate` 的起止、长任务、DOM 的大批变动与 `data-rune-ready` 的时刻。

### 首屏分批接管（2026-11-14）

接管为什么慢（读 Blazor 的源码、按阶段打点、原生 CPU 采样得到的）：

- Blazor 不复用预渲染的 DOM（没有 hydration）：根组件第一次渲染时把预渲染的节点清掉，整页重新渲染一遍，而且是一个不让出主线程的任务。
- .NET 在浏览器里解释执行，而且这是第一次：采样里只有约三分之一的时间在执行代码，其余是方法的第一次翻译（约 15%）、类型与泛型的解析（约 21%）、运行时别的开销与分配。
- 分阶段（Button 页，热缓存）：运行时启动到 Main 约 0.5 秒、建主机 0.4 秒、到根组件第一次渲染 1.1 秒（路由表反射 0.4～0.65 秒在里面）、外壳 0.65 秒、页头 0.65 秒、
  示例与 API 表约 2 秒。前面约 3 秒哪一页都有；示例那一段随页面变，DataTable 页是 5.7 秒。

改法：示例一节一节排队渲染（原来只在站内换页后排，第一页一口气渲染完），预渲染的内容留着当占位。

- 预渲染时每一节两头留注释标记（`Queued` 的 `Hold`）；交互接管时这一节先只渲染一个空的占位，文档站的 JS 初始化器
  （`Rune.Docs.Content.lib.module.js`）在同一个任务里把预渲染的那段节点放回占位，画面不变；轮到时换成真正渲染的内容。
- 队列每攒够 60 毫秒才让出一次主线程（`RenderQueue`）：每节都让的话，轻的十几节各带一次整页的排版与绘制。
- 端到端测试的“可以操作了”（`data-demo-interactive`）改成交互且队列排完；`TakeoverTests` 逐帧检查效果区没有空过。

本地导出的站点、热缓存、无头 Chromium，从 WebAssembly 实例化完算起（三次取中位数）：

| 页面 | 第一批换上（外壳可以操作） | 全部换完 | 最长的一次卡顿 |
| ---- | -------------------------- | -------- | -------------- |
| Button（17 节） | 3.6 秒 → 2.6 秒 | 4.5 秒 → 5.1 秒 | 2.5 秒 → 1.4 秒 |
| DataTable（23 节） | 7.8 秒 → 2.9 秒 | 10.5 秒 → 12.9 秒 | 7.4 秒 → 1.6 秒 |
| 指南（没有示例） | 2.7 秒 → 3.0 秒（出入之内） | 2.9 秒 → 3.0 秒 | 1.6 秒 → 1.7 秒 |

全部换完变慢是分批的代价，不是 .NET 多算了（DataTable 页 .NET 的时间 7.55 秒 → 7.63 秒）：浏览器的排版从 1.2 秒到 2.7 秒、绘制与预绘制多约 1 秒——
预渲染的节点放回占位要重新排一遍版，每批换上后又排一遍、画一遍。换来的是不再整页冻住：第一批之后可以滚动、点导航，示例从上往下陆续可用。
还能省的（没做）：视口外的占位先只留高度，滚到附近再把预渲染的节点放回去，省掉中间那一遍排版。

## 4. 待议项（结构性的，先不动）

| 项 | 现状与数字 | 方向 | 取舍 |
| -- | ---------- | ---- | ---- |
| 选项弹出层关着也渲染选项 | Select、Combobox 的列表一直在 DOM 里（多时虚拟滚动） | 交互模式下第一次打开才渲染（同 Dialog 的 Lazy） | 关着时按字母选中、原生 popover 打开不往返都依赖列表在 DOM 里，改了要另想办法；静态 SSR 仍要一开始就渲染 |
| 参数比较的装箱 | 每个值类型参数一次装箱、按名字查一次属性（6 个参数约 0.5 µs） | 由源代码生成器为组件生成按类型比较的代码（Rune.Generators 已有） | 收益看父级重渲染的频率；生成器要覆盖继承的参数 |
| 库的使用方也有“JS 装好得晚”的问题 | 文档站用 `ModulePreloads`（读发布目录算出要预加载的模块）解决了，这个组件在 apps/Rune.Docs 里，库里没有 | Rune.UI 提供一个放在 head 里的组件，模块清单在构建时生成 | 要多一个生成步骤（或运行时读静态资源），先看有没有使用方需要 |
| JS 不压缩、不打包 | 约 270 KB（一半是注释），开发时未压缩；发布时 MapStaticAssets 有 br / gzip | 构建时去注释或打包成一个文件 | 打包要引入构建步骤（node），与“浏览器原生 ES 模块、不打包”的现有约定冲突；入口拆分后模块已不在启动的关键路径上 |
| 快捷键查找 | 每次按键在整个文档里找 `[data-rune-hotkey]` | 插入时登记 | 要保持文档顺序的匹配语义，开销小，暂不改 |
