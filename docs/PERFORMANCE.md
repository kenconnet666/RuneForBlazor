# 性能：探测、优化与待议项

每次渲染都走的路径（样式定义的查找、属性合并、样式登记、参数比较、依赖收集）与浏览器端的初始化、DOM 变化处理。
基准在 `tests/Rune.Benchmarks`（BenchmarkDotNet，见它的 README）；浏览器端的数字是在文档站（Release、本机、HTTP/1.1、未压缩）里用 Performance API 与给
`querySelectorAll` / `matches` 计数量的。

计时类基准要在机器空闲时跑：2026-11-06 那一轮跑的时候机器平均负载 80% 以上（WSL、IDE 在后台），渲染基准的耗时前后差到 60%，
所以渲染只看**分配量**（确定的），耗时看微基准（倍数差远大于噪声）。

## 1. 2026-11-06 这一轮

### C#：每次渲染的路径

| 路径 | 之前 | 之后 | 改法 |
| ---- | ---- | ---- | ---- |
| `Css.Define`（静态） | 26 ns / 24 B | 20 ns / 0 B | `GetOrAdd` 用带状态的重载，不再每次分配闭包 |
| `Css.Define`（按键：档位、配方） | 52 ns / 56 B | 25 ns / 0 B | 按键与结果的类型分开放（`Keyed<TKey, T>`），键不装箱；热重载时一起清 |
| `Recipe.Of`（图标的配方） | 125 ns / 136 B | 79 ns / 0 B | 同上（配方的键是元组） |
| `Attrs.Merge`（只有样式） | 54 ns | 7 ns | 已编译的样式记住最近登记进的登记表，同一作用域里不再加锁查表 |
| `Attrs.Merge`（部件层：样式 + `data-scope` / `data-part`） | 296 ns / 304 B | 7 ns / 0 B | 合并结果记在最靠后的非空层上，同样的几层（引用相同，Attrs 创建后不变）直接复用 |
| `Attrs.Merge`（部件 + Rest + 受管） | 625 ns / 816 B | 13 ns / 0 B | 同上 |
| `Attrs.MergeProps` / `Layer` | 518 ns / 960 B | 4 ns / 0 B | 同上；结果是同一个对象，子组件按引用比较 `Sx` 参数时就会跳过渲染 |
| 依赖收集（不读信号的组件） | 每次渲染一个字典、一个 HashSet | 不分配 | 读到信号时才建字典，没有依赖时订阅集合为 null |
| 整页渲染（按钮、徽标、图标各 100 个） | 首次 1579 KB；父级重渲染、子组件不变 131 KB；按钮全部重渲染 360 KB | 1344 KB；71 KB；217 KB | 以上各项合计 |
| 参数比较（6 个参数） | 520 ns / 72 B | 不变 | 试过 `MethodInvoker` 代替 `PropertyInfo.GetValue`，没有差别，撤回；剩下的是枚举、布尔的装箱与按名字查属性（见待议项） |

`RuneStyles` 在新规则登记时排一次渲染：之前每条规则排一次（第一次渲染一页登记几百条），现在排着队时不再排。

另：bUnit 不适合测渲染性能。它每渲染一个组件就重新生成整页 HTML 再解析，组件一多就是平方级（100 组按钮改一个参数要 183 ms、105 MB），
盖过了要测的东西。基准用自己的最小渲染器（`BenchRenderer`：只有 Blazor 的渲染与比较，没有输出）。

### 浏览器：启动与 DOM 变化

| 项 | 之前 | 之后 | 改法 |
| -- | ---- | ---- | ---- |
| Blazor 启动前等的 JS | 初始化器连同它静态导入的约 40 个模块（本机从初始化器到最后一个模块约 0.7 s，WebAssembly 运行时在这之后才开始下载） | 只等 24 KB 的入口；主体（`js/core/runtime.js` 与模块）在入口执行时开始后台加载，与 WebAssembly 运行时的下载并行 | 入口同步注册自定义事件，并在 document 上为每种事件占位（保持排在 Blazor 的事件委托之前：先不占位时，负载高的 WebAssembly 端到端测试里 Combobox 的高亮被清掉），主体到了再挂处理函数 |
| 增强导航进入 Select 文档页（约 2800 个新元素）时找要处理的元素 | `querySelectorAll` 2833 次（30 ms）、`matches` 约 10.7 万次（89 ms） | 42 次（3 ms）、1437 次（2 ms） | Blazor 先插父元素再逐个插子元素，一棵新子树每个节点各有一条变化记录：只从这一批最外层的新节点往下找；根节点先用合并的选择器问一次；列表、标签行按元素去重，每批处理一次 |
| 跟随指针的装饰（`data-rune-pointer`） | 鼠标一动，每帧在整个文档里找一遍（页面上没有这种元素也找） | 插入时登记，每帧只走登记的；一个都没有时不排帧 | |

## 2. 分段输出与级联层之后（2026-11-06，vue-tsx-pro 阶段 1）

- 合并路径的耗时、分配不变（结果按层缓存，分段只在第一次合并时多编译几段）；整页渲染的分配：首次 1344 → 1351 KB，按钮全部重渲染 217 → 220 KB。
- 样式文本（测试台的静态页，含主题变量）：Button 508 → 515 KB、Select 296 → 297 KB、Table 272 → 271 KB、Form 336 → 334 KB、Card 289 → 291 KB。
  演示页上定制、`Sx` 的组合不多，分段省下的少，每条规则外面多包的 `@layer rune.s{k}{…}` 又多了一点；组合多的应用（同一组件多种档位 × 定制 × 使用方样式）才省得明显。
- 计算样式：`tools/style-snapshot` 前后比对全部文档页（亮暗两套、强制 :hover / :focus-visible / :active），真实差异为 0
  （差异只有改了文字的样式指南页、动画中途的取值，以及改造前那份在两个元素上亮暗不一致的不稳定值）。

## 3. 待议项（结构性的，先不动）

| 项 | 现状与数字 | 方向 | 取舍 |
| -- | ---------- | ---- | ---- |
| 主题变量内联在每个响应里 | 文档站一页约 200 KB 样式文本，其中 105 KB 是全部主题的变量（开了 16 套主题，切换不用往返）；每次整页加载、增强导航都重新下载，浏览器缓存不了 | 主题变量做成静态样式表（构建时由主题生成，或启动时生成、带指纹与长缓存），页面只引用 | 需要改 `RuneProvider` / 主题启动脚本的输出方式；只用亮暗两套的应用收益小 |
| 选项弹出层关着也渲染选项 | Select、Combobox 的列表一直在 DOM 里（多时虚拟滚动） | 交互模式下第一次打开才渲染（同 Dialog 的 Lazy） | 关着时按字母选中、原生 popover 打开不往返都依赖列表在 DOM 里，改了要另想办法；静态 SSR 仍要一开始就渲染 |
| 参数比较的装箱 | 每个值类型参数一次装箱、按名字查一次属性（6 个参数约 0.5 µs） | 由源代码生成器为组件生成按类型比较的代码（Rune.Generators 已有） | 收益看父级重渲染的频率；生成器要覆盖继承的参数 |
| JS 不压缩、不打包 | 约 270 KB（一半是注释），开发时未压缩；发布时 MapStaticAssets 有 br / gzip | 构建时去注释或打包成一个文件 | 打包要引入构建步骤（node），与“浏览器原生 ES 模块、不打包”的现有约定冲突；入口拆分后模块已不在启动的关键路径上 |
| 快捷键查找 | 每次按键在整个文档里找 `[data-rune-hotkey]` | 插入时登记 | 要保持文档顺序的匹配语义，开销小，暂不改 |
